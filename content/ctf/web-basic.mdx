# Web 基础：参数污染

先定位参数进入业务逻辑的位置，再比较不同解析器对重复参数的处理差异。

## 题目

给定一个看起来很普通的查询接口，目标是理解服务端实际取到的参数值，而不是浏览器地址栏里“看起来”的值。

## 分类

Web / 逻辑类。难度不高，但容易因为“我以为参数就是这样解析的”而走偏。

## Writeup

### 1. 找入口

先确认参数从哪里进来：

- query string
- body
- 被中间层改写过的 header

然后问一个具体问题：如果同一个名字出现两次，框架取哪一个？

### 2. 做最小对比

```http title="request.http"
GET /item?id=1&id=2 HTTP/1.1
Host: challenge.local
```

分别观察：

- 覆盖：后值覆盖前值
- 拼接：`1,2`
- 数组化：`["1", "2"]`

### 3. 以服务端为准

前端、WAF、应用框架可能各自解析一次。最终以服务端业务代码实际使用的值为准。

> 不要把“我本地 curl 看到的”直接当成应用内部拿到的结构。

## 收获

参数污染不是炫技，而是提醒自己：输入边界、解析器和业务取值路径必须分开看。
